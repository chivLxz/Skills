# 项目思维导图

把项目、代码库或文档读懂，然后产出一张**多层、能改、说人话、能交付**的结构图。

## 四条铁律

1. **不套模板。** 一级分支怎么切，由你读到的内容和用户的目的共同决定，不是从菜单里挑一个。同一个项目，用户想「讲清它怎么跑」和想「排接下来的活」，图的长相应该完全不一样。
2. **说读图的人听得懂的话。** 深度往下走，**术语不跟着往下掉**。同一个事实，产品经理要的是「采样率 16 kHz、监测间隔 1500 ms」，只有工程师才关心 `USE_PCM_STREAMING=1`。落笔前先定受众，再定停在哪个术语层级 —— 一份挖到 6 层、节点全是环境变量的图，等同于没画。
3. **深度由信息决定，不由格式决定。** 不要因为「图会变大」就停在两三层。一个节点该不该继续拆，只问一个问题：**它下面还有没有独立可说的东西**。有就往下走，没有就停。浅的图不等于简洁，那是没读完。
4. **先出大纲，再转格式。** Markdown 是唯一真相来源。大纲人能手改、能 diff、能进 Git；改完重跑转换就行，分析结论不会丢。跳过这步直接生成 `.xmind` 等于放弃可修改性。

## 第 1 步：先弄清这张图要干什么

图是给人看的，所以先确定三件事：

| 要确定的 | 影响什么 |
|---|---|
| **范围** | 整个项目，还是某个子系统、某条链路、某次变更 |
| **用途** | 自己搞懂 / 给人交接 / 汇报评审 / 排期分工 / 对外交付 |
| **受众** | 自己、产品与业务、同组工程师、跨部门、客户 —— 决定用多少术语、粒度粗还是细 |

**能推断就别问**：用户说「帮我把这个项目画成导图」，通常就是要一份全景理解图；说「给客户梳理交付拓扑」，就是要按部署与依赖来切。只有当范围或受众**真的无从判断、且选错会让整张图跑偏**时，才问一句——只问一句，把选项也一并给出。

### 受众决定「表达层级」

定完受众，立刻定这张图**停在哪个术语层级**。这一步和定深度同等重要 —— 层级选错，图再深也白画。落笔前把它写下来（「这张图按产品层写」），后面所有节点都按它执行。

| 表达层级 | 适配受众 | 节点里出现什么 |
|---|---|---|
| **产品 / 业务层**（默认） | 产品经理、业务方、跨部门、客户、汇报评审 | 可感知的行为、参数、指标、约束。**不出现任何代码标识符** |
| **工程层** | 同组工程师、代码交接、排期分工 | 产品层的内容 + 模块名 / 接口名 / 文件路径（**路径只进备注，不进标题**） |

**拿不准就按产品层写。** 工程师看得懂「采样率 16 kHz」，产品经理看不懂 `USE_PCM_STREAMING=1`。反过来才是真的信息损失 —— 所以宁可少写代码细节，不要多写。

### 术语闸门：什么能进节点，什么不能

每一个**节点标题**落笔前问一句：**这个字符串，是给「要用这张图的人」看的吗？** 只有翻代码的人才能理解的，就不该出现在标题里。

| ✅ 保留（产品经理必须知道） | ❌ 剔除（只在代码里有意义） |
|---|---|
| **性能与体验**：采样率 16 kHz、端到端时延 < 200 ms、唤醒响应 800 ms | **环境变量与开关**：`USE_PCM_STREAMING=1`、`ENABLE_XXX=0` |
| **时序与节奏**：1500 ms 监测间隔、300 ms 静音判定、30 s 请求超时 | **函数名 / 类名 / 变量名**：`parse_config()`、`AudioFrontend`、`cfg.retry` |
| **阈值与判定**：置信度阈值 0.7、唤醒词 2 音节、误唤醒 ≤1 次/天 | **文件路径 / 目录名**：`src/audio/aec.py`、`internal/serializer.js` |
| **容量与规模**：并发 8 路、单机 16 路麦、内存占用 < 2 GB | **构建与依赖内部名**：编译选项、锁文件、内部包名、镜像 tag |
| **质量指标**：ASR 准确率、声纹 EER、召回率、误报率 | **自造缩写**（行业通用的 ASR / AEC / VAD / WebRTC 可以留） |
| **兼容与约束**：支持平台、协议标准（WebRTC、ONVIF）、算力下限 | **纯实现手法**：「用哈希表缓存」这类没有业务含义的写法 |

一句话区分：**参数值要看，实现手段不要看。** 「采样率 16 kHz」是产品定义 —— 它影响体验、影响验收、影响选型；「`USE_PCM_STREAMING=1`」只是这个定义在某份代码里的一种实现方式，换个代码库就不存在了。

**同一个事实的两种写法**，照着右边写：

| ❌ 别写 | ✅ 写成 |
|---|---|
| `USE_PCM_STREAMING=1` / `USE_OPUS_STREAMING=0` | 音频走 PCM 流式传输（未启用 Opus 压缩） |
| `AEC_REF_ALIGN_MS=40` | 回声消除参考对齐 40 ms |
| `_vad_silence_timeout` 默认 800 | 静音判定窗口 800 ms |
| 调 `parse_config()` 读 `cfg.max_conn` | 单实例最大连接数可配置（默认 8） |
| 依赖 `internal/serializer.js` | 依赖内部序列化模块（无外部依赖） |

## 第 2 步：侦察（两轮，先建地图再定向深读）

**素材决定深度上限。** 只扫一遍入口文件，后面想挖也挖不动 —— 这是产出浅图的第一大原因。

**第一轮 · 建地图**（约 10～20 个文件）

1. `README*`、`docs/` 入口、`ARCHITECTURE*`、`CONTRIBUTING*`
2. 依赖清单：`package.json`、`pyproject.toml`、`requirements.txt`、`go.mod`、`Cargo.toml`、`pom.xml`、`build.gradle`
3. 顶层目录树（`ls` / `find -maxdepth 2`，**不要递归全量读取**）
4. 入口文件、路由表、主配置、部署脚本

产出：这是什么类型的项目、用了什么技术栈、功能边界的天然分界在哪。

**第二轮 · 定向深读**（按分支，每个一级分支 3～10 个文件）

第一轮定下一级分支后，**逐个分支去找它的实现**：

- 从目录名 / 文件名定位该分支的源码位置
- 读它的入口、接口定义、核心流程、配置项
- 目标是拿到**具体符号**：类名、函数名、配置键、参数默认值

> **这些符号是给你自己定位用的，不是往图上抄的。** 拿到 `USE_PCM_STREAMING=1` 之后，你才算真的读懂了这一层的实现；但落到节点上要写成它的产品含义（「音频走 PCM 流式传输」）。读的时候越具体越好，写的时候越通俗越好 —— 这两件事不冲突。

带着一个问题去读：**「要把这个分支展开到 5 层，我现在还缺什么信息？」** 只读能回答这个问题的文件，不要漫游式遍历。

整体读取量控制在 **80 个文件以内**。信息不足就停下来告诉用户缺什么，**不要靠猜补齐** —— 编出来的结构比没有更糟，它会让人基于错的地图做决策。

## 第 3 步：定骨架与深度预算

**中心主题** —— 项目或主题名，一个名词短语。

**一级分支** —— 数量控制在 4～7 个，划分依据从内容和用途倒推。下面这些是**思路示例，不是选项菜单**：

- 讲「它由什么组成」→ 按运行时组件 / 子系统切
- 讲「它怎么跑起来」→ 按启动链路 / 数据流阶段切
- 讲「代码怎么组织」→ 按代码模块 / 目录边界切
- 讲「怎么交付上线」→ 按环境 / 部署单元 / 依赖 / 配置切
- 讲「接下来做什么」→ 按工作包 / 里程碑切
- 讲「为什么这么设计」→ 按设计决策 / 约束 / 取舍切

判定标准只有一条：**一级分支之间互斥，合起来覆盖用户关心的全部内容（MECE）**。同一个东西不能同时挂在两个分支下；用户关心的东西不能没有位置。

**深度预算** —— 不同分支不该一样深。平均用力会把图做成一张均匀的浅网：

| 分支类型 | 目标深度 | 怎么判断 |
|---|---|---|
| **主干** | 5～7 层 | 用户明确点名的、问题答案所在的、系统的核心链路 |
| **支撑** | 3～5 层 | 主干直接依赖的、服务于主干的 |
| **外围** | 2～3 层 | 背景、环境、边缘功能；有它更好，但用户不会追问 |

动手前先花 30 秒把各个一级分支分到这三档里。**深处的细节优先给主干** —— 一张「主干到 7 层、外围到 2 层」的图，比一张「所有分支都 4 层」的图有用得多。

## 第 4 步：逐层展开

这一步决定图的深度。对每个节点问同一句话：**「它下面还有没有独立可说的东西？」** 有，就接着拆。

拿不准从哪拆时，用这五个角度轮一遍，命中哪个用哪个：

| 角度 | 问法 | 示例 |
|---|---|---|
| **组成** | 它由哪些部分组成？ | 语音前端 → 麦克风阵列 / 3A 算法 / 声纹识别 |
| **机制** | 它内部怎么运作？分几步？ | AEC → 参考信号对齐 → 非线性残留抑制 |
| **接口** | 它对外暴露什么？输入输出是什么？ | 转写服务 → 流式输入 / 分段输出 |
| **参数** | 有哪些关键配置、阈值、数值？ | ANS → 降噪等级 / 尾音时长 / 采样率 |
| **依赖** | 它依赖谁？被谁依赖？ | 声纹识别 → 依赖 VAD；被说话人归因调用 |

不必每个节点都过五个角度 —— 走到哪个角度能出东西，就用哪个。

**什么时候停（叶子判定）** —— 节点落成下面任意一种，就该停：

- 具体的参数值 / 阈值 / 时间间隔 —— **16 kHz、1500 ms、置信度 0.7**
- 具体的行为描述，读完就知道「它做了什么、什么时候触发」
- 一条不能再分的职责

**代码标识符不算「更深一层」。** 文件名、函数名、环境变量、开关名不是更细的分析，是换了一种语言。产品层的图里它们一律不进标题；工程层的图里也只进备注。

**深度和术语是两条独立的轴。** 一个节点可以从第 2 层挖到第 6 层，全程都停在产品层：

```
语音前端
  └ 音频采集
      └ 上行传输
          └ 编码格式          ← 还是产品层
              └ 走 PCM 流式传输，未启用 Opus 压缩   ← 到叶子了，但没掉进代码
```

如果非要写 `USE_PCM_STREAMING=1` 才能说清，说明**这个节点本身还没被理解** —— 先把它的产品含义写出来，写不出来就停在这一层。

还没到叶子、但你手上已经没有依据了 —— 也停，**标上 `⚠`**，不要编。

**不要为了凑深度硬拆。** 把「一键启动」拆成「按电源键 / 等待加载」是凑数，不是分析。往下拆必须能说出**新的、用户会关心的事实**。

## 第 5 步：写 Markdown 大纲

落到 `./mindmap/<主题>.md`。

**语法** —— Markdown 标题只有 6 级，够不到 5 层以上，所以两种写法混着用：

````markdown
# 中心主题

## 一级分支
### 二级分支
#### 三级分支
##### 四级分支
###### 五级分支
- 六级分支（列表顶格）
  - 七级分支（每缩进 2 空格加一级）
    - 八级分支
````

- `#` 是中心主题，只有一个
- `##` ~ `######` 给前 5 层，可读性最好，**主干优先用标题**
- 更深处用嵌套列表接着写，**层数不设上限**
- 标题和列表可以在同一份大纲里自由混用

**硬约束：**

1. **主干分支要展开到 5～7 层**，不要停在 3 层就收工
2. 节点文字 **≤16 字**，写「名词 + 关键限定」，不写整句
3. 节点要具体，而不是泛泛的名词；但**具体 ≠ 代码化**。三个档位：

   | 太泛（差） | 具体（好） | 太技术（差） |
   |---|---|---|
   | 回声消除 | 回声消除参考对齐 40 ms | `AEC_REF_ALIGN_MS=40` |
   | 性能优化 | 端到端时延 < 200 ms | `ENABLE_TRT=1` |
   | 配置项 | 采样率 16 kHz / 位深 24 bit | `AUDIO_FMT=pcm_s16le` |

   往右一列是**用代码注释当分析结论** —— 它不比左边那列好，只是更难看懂。
4. 一级分支 4～7 个；某分支只有 1 项就并进兄弟分支，超过 8 项就再拆一层
5. 同一父节点下子节点数量大致均衡，避免「一条巨肢 + 三条残肢」
6. **节点的标题里不允许出现代码标识符** —— 环境变量、开关名、函数名、类名、文件路径一律不进标题。工程层的图可以把位置写进行内代码（`` 参考信号对齐 `src/audio/aec.py` ``），转换时会自动收进「备注」；**产品层的图连备注都不用写**，读图的人不会去翻代码
7. 属于推断、没有直接证据的节点，文字里标 `⚠`（转成「待复核」标签 / 橙色下划线）
8. **绝不编造**模块名、接口名、配置项、文件路径

写完后逐层扫一遍：**有没有哪个节点，是「只有读过这份代码的人才懂」的？** 有就改写成它的产品含义，写不出来就删掉。

## 第 6 步：转成产物

```bash
# 可编辑的 .xmind（Xmind 桌面/移动/网页版均可直接打开继续编辑）
python3 <skill-dir>/scripts/md2xmind.py ./mindmap/<主题>.md ./mindmap/<主题>.xmind

# SVG（矢量源文件）+ PNG（高清图）+ PDF（单页矢量）
python3 <skill-dir>/scripts/render.py ./mindmap/<主题>.md --outdir ./mindmap
```

`<skill-dir>` 就是本 SKILL.md 所在目录。两个脚本都是零第三方依赖的纯 Python。

常用参数：

- `md2xmind.py --structure logic-right` —— 换成逻辑图/树形图/组织架构图等布局（默认 `unbalanced` 思维导图）
- `md2xmind.py --title "标题"` —— 覆盖中心主题
- `render.py --only svg,png` —— 只要其中某几种
- `render.py --scale 4` —— 指定超采样倍率（默认按画布自动选）
- `render.py --layout wing` —— 强制两翼布局（默认 `auto`：节点多到图变成窄长条时自动切两翼）

**产物清单**

| 文件 | 能改吗 | 用途 |
|---|---|---|
| `.md` | ✅ 纯文本 | 真相来源。改这个，然后重跑上面两条命令 |
| `.xmind` | ✅ Xmind 里直接编辑 | 交付、协作、二次加工 |
| `.svg` | ✅ 矢量，Illustrator / Figma / Inkscape 可编辑 | 精修排版、嵌网页 |
| `.png` | ❌ 图片 | 贴文档、发消息、插 PPT |
| `.pdf` | ❌ 矢量单页 | 打印、正式汇报 |

**失败处理**（不要伪造文件，也不要声称已经生成）：

- 没装 Chrome/Edge/Chromium → `.svg` 仍然会生成，直接告诉用户 PNG/PDF 需要浏览器，或让他用矢量工具自行导出
- 想编辑 `.xmind` 但没有 Xmind → Xmind 免费版可永久编辑本地文件（只有导出 PNG/PDF 才需订阅）；也可用其他支持 `.xmind` 的工具导入

## 图装不下了怎么办

深度放开后，图会变大。**不要靠砍深度来控制规模**，靠拆图：

单张图节点超过约 **180 个**，或某个一级分支自己就超过约 **60 个节点**时，拆成「总览图 + 分支详图」：

- **总览图** —— 全部一级分支，最多到 2～3 层，让人一眼看清全局
- **分支详图** —— 那个庞大的分支单独成图，从自己开始一路展开到叶子

各自是独立的 `.md` 文件，各自转换。别把它们硬塞进一个文件。

## 第 7 步：收尾

给一份简短回执：

- 产物路径清单
- **这张图的术语口径**：产品层还是工程层
- **深度统计**：最大层数 / 主干分支到了第几层
- 节点统计：各层节点数、总数
- 哪些节点标了 `⚠`、为什么（是推断，还是读到一半缺依据）
- 一句话：**改 `.md` 后重跑第 6 步即可，不用重做分析**

## 反模式

- **不要把代码标识符搬进节点** —— 环境变量、开关名、函数名、类名、文件路径是代码的行话，不是图的语言。出现一个就是漏改
- **不要把「实现手段」当成「分析深度」** —— `USE_PCM_STREAMING=1` 不比「音频走 PCM 流式传输」更深，它只是更难懂
- **不要因为「图会变高」就砍深度** —— 该深的地方浅了，图就白画了
- **不要平均用力** —— 主干要深、外围要浅，均匀的浅网没有信息量
- **不要只列名词就收工** —— 「模块 A / 模块 B / 模块 C」是目录，不是分析
- **不要为了凑层数硬拆** —— 拆下去得能说出新事实，否则就是注水
- 不要跳过大纲直接生成 `.xmind` —— 等于放弃了可修改性
- 不要套用固定视图模板 —— 一级分支必须从内容推导出来
- 不要把整句话塞进节点，解释放备注或正文
- 不要读全量代码再画图，成本失控且容易跑偏
- 不要编造结构；宁可少画几个节点，也不要填一个不存在的东西

## 降级：接手一份已经画好的大纲

如果用户拿来一份**已有的 `.md` 大纲**要你清理（通常是别的工具生成的、术语层级不对），按这个顺序过：

1. **先定表达层级** —— 问清给谁看（默认产品层）
2. **逐节点扫术语闸门** —— 命中「❌ 剔除」那列的全部改写：能还原产品含义的就改写（`USE_PCM_STREAMING=1` → 音频走 PCM 流式传输），还原不出来的直接删
3. **查叶子是不是掉进了代码** —— 深层节点如果只剩标识符，说明原始分析没做透；这种情况标出来告诉用户，**不要硬猜它的含义**
4. **保留所有参数、阈值、时序数字** —— 这些不是技术细节，是产品事实（16 kHz、1500 ms、置信度 0.7 一个都别丢）
5. 重新转换产物，并在回执里说清改了哪些、删了哪些、哪些是猜的

## 宿主适配

- 不需要 subagent，Codex CLI / Claude Code / 其他 Agent 均可跑
- 只用到「读文件 / 写文件 / 执行命令」三种能力，遵守宿主的权限与审批规则
- 写文件被拦时，说清缺什么权限，**不要假装已经保存**
- 生成 PNG/PDF 要调本机浏览器，若宿主沙箱禁止启动外部进程，走 `.svg` + 提示用户的路径
