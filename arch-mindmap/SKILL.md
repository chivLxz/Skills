# 项目思维导图

把项目、代码库或文档读懂，然后产出一张**多层、能改、能交付**的结构图。

## 三条铁律

1. **不套模板。** 一级分支怎么切，由你读到的内容和用户的目的共同决定，不是从菜单里挑一个。同一个项目，用户想「讲清它怎么跑」和想「排接下来的活」，图的长相应该完全不一样。
2. **深度由信息决定，不由格式决定。** 不要因为「图会变大」就停在两三层。一个节点该不该继续拆，只问一个问题：**它下面还有没有独立可说的东西**。有就往下走，没有就停。浅的图不等于简洁，那是没读完。
3. **先出大纲，再转格式。** Markdown 是唯一真相来源。大纲人能手改、能 diff、能进 Git；改完重跑转换就行，分析结论不会丢。跳过这步直接生成 `.xmind` 等于放弃可修改性。

## 第 1 步：先弄清这张图要干什么

图是给人看的，所以先确定三件事：

| 要确定的 | 影响什么 |
|---|---|
| **范围** | 整个项目，还是某个子系统、某条链路、某次变更 |
| **用途** | 自己搞懂 / 给人交接 / 汇报评审 / 排期分工 / 对外交付 |
| **受众** | 自己、同组工程师、跨部门、客户 —— 决定用多少术语、粒度粗还是细 |

**能推断就别问**：用户说「帮我把这个项目画成导图」，通常就是要一份全景理解图；说「给客户梳理交付拓扑」，就是要按部署与依赖来切。只有当范围或受众**真的无从判断、且选错会让整张图跑偏**时，才问一句——只问一句，把选项也一并给出。

## 第 2 步：侦察（两轮，先建地图再定向深读）

**素材决定深度上限。** 只扫一遍入口文件，后面想挖也挖不动 —— 这是产出浅图的第一大原因。

**第一轮 · 建地图**（约 10～20 个文件）

1. `README*`、`docs/` 入口、`ARCHITECTURE*`、`CONTRIBUTING*`
2. 依赖清单：`package.json`、`pyproject.toml`、`requirements.txt`、`go.mod`、`Cargo.toml`、`pom.xml`、`build.gradle`
3. 顶层目录树（`ls` / `find -maxdepth 2`，**不要递归全量读取**）
4. 入口文件、路由表、主配置、部署脚本

产出：这是什么类型的项目、用了什么技术栈、功能边界的天然分界在哪。

**第二轮 · 定向深读**（按分支，每个一级分支 3～10 个文件）

第一轮定下一级分支后，**逐个分支去找它的实现**：

- 从目录名 / 文件名定位该分支的源码位置
- 读它的入口、接口定义、核心流程、配置项
- 目标是拿到**具体符号**：类名、函数名、配置键、参数默认值

带着一个问题去读：**「要把这个分支展开到 5 层，我现在还缺什么信息？」** 只读能回答这个问题的文件，不要漫游式遍历。

整体读取量控制在 **80 个文件以内**。信息不足就停下来告诉用户缺什么，**不要靠猜补齐** —— 编出来的结构比没有更糟，它会让人基于错的地图做决策。

## 第 3 步：定骨架与深度预算

**中心主题** —— 项目或主题名，一个名词短语。

**一级分支** —— 数量控制在 4～7 个，划分依据从内容和用途倒推。下面这些是**思路示例，不是选项菜单**：

- 讲「它由什么组成」→ 按运行时组件 / 子系统切
- 讲「它怎么跑起来」→ 按启动链路 / 数据流阶段切
- 讲「代码怎么组织」→ 按代码模块 / 目录边界切
- 讲「怎么交付上线」→ 按环境 / 部署单元 / 依赖 / 配置切
- 讲「接下来做什么」→ 按工作包 / 里程碑切
- 讲「为什么这么设计」→ 按设计决策 / 约束 / 取舍切

判定标准只有一条：**一级分支之间互斥，合起来覆盖用户关心的全部内容（MECE）**。同一个东西不能同时挂在两个分支下；用户关心的东西不能没有位置。

**深度预算** —— 不同分支不该一样深。平均用力会把图做成一张均匀的浅网：

| 分支类型 | 目标深度 | 怎么判断 |
|---|---|---|
| **主干** | 5～7 层 | 用户明确点名的、问题答案所在的、系统的核心链路 |
| **支撑** | 3～5 层 | 主干直接依赖的、服务于主干的 |
| **外围** | 2～3 层 | 背景、环境、边缘功能；有它更好，但用户不会追问 |

动手前先花 30 秒把各个一级分支分到这三档里。**深处的细节优先给主干** —— 一张「主干到 7 层、外围到 2 层」的图，比一张「所有分支都 4 层」的图有用得多。

## 第 4 步：逐层展开

这一步决定图的深度。对每个节点问同一句话：**「它下面还有没有独立可说的东西？」** 有，就接着拆。

拿不准从哪拆时，用这五个角度轮一遍，命中哪个用哪个：

| 角度 | 问法 | 示例 |
|---|---|---|
| **组成** | 它由哪些部分组成？ | 语音前端 → 麦克风阵列 / 3A 算法 / 声纹识别 |
| **机制** | 它内部怎么运作？分几步？ | AEC → 参考信号对齐 → 非线性残留抑制 |
| **接口** | 它对外暴露什么？输入输出是什么？ | 转写服务 → 流式输入 / 分段输出 |
| **参数** | 有哪些关键配置、阈值、数值？ | ANS → 降噪等级 / 尾音时长 / 采样率 |
| **依赖** | 它依赖谁？被谁依赖？ | 声纹识别 → 依赖 VAD；被说话人归因调用 |

不必每个节点都过五个角度 —— 走到哪个角度能出东西，就用哪个。

**什么时候停（叶子判定）** —— 节点落成下面任意一种，就该停：

- 具体的文件名 / 路径
- 具体的类名 / 函数名 / 接口名
- 具体的配置项 / 参数值 / 阈值
- 一条不能再分的职责描述

还没到这些层级、但你手上已经没有依据了 —— 也停，**标上 `⚠`**，不要编。

**不要为了凑深度硬拆。** 把「一键启动」拆成「按电源键 / 等待加载」是凑数，不是分析。往下拆必须能说出**新的、用户会关心的事实**。

## 第 5 步：写 Markdown 大纲

落到 `./mindmap/<主题>.md`。

**语法** —— Markdown 标题只有 6 级，够不到 5 层以上，所以两种写法混着用：

````markdown
# 中心主题

## 一级分支
### 二级分支
#### 三级分支
##### 四级分支
###### 五级分支
- 六级分支（列表顶格）
  - 七级分支（每缩进 2 空格加一级）
    - 八级分支
````

- `#` 是中心主题，只有一个
- `##` ~ `######` 给前 5 层，可读性最好，**主干优先用标题**
- 更深处用嵌套列表接着写，**层数不设上限**
- 标题和列表可以在同一份大纲里自由混用

**硬约束：**

1. **主干分支要展开到 5～7 层**，不要停在 3 层就收工
2. 节点文字 **≤16 字**，写「名词 + 关键限定」，不写整句
3. 节点要具体，而不是泛泛的名词。对比：

   | 太泛（差） | 具体（好） |
   |---|---|
   | 回声消除 | AEC 参考信号对齐 |
   | 性能优化 | TensorRT INT8 量化 |
   | 配置项 | 采样率 16kHz / 位深 24bit |

4. 一级分支 4～7 个；某分支只有 1 项就并进兄弟分支，超过 8 项就再拆一层
5. 同一父节点下子节点数量大致均衡，避免「一条巨肢 + 三条残肢」
6. 有代码依据的节点，用行内代码标出位置：`` 参考信号对齐 `src/audio/aec.py` ``
   —— 转 `.xmind` 时会自动收进「备注」，标题保持干净
7. 属于推断、没有直接证据的节点，文字里标 `⚠`（转成「待复核」标签 / 橙色下划线）
8. **绝不编造**模块名、接口名、配置项、文件路径

## 第 6 步：转成产物

```bash
# 可编辑的 .xmind（Xmind 桌面/移动/网页版均可直接打开继续编辑）
python3 <skill-dir>/scripts/md2xmind.py ./mindmap/<主题>.md ./mindmap/<主题>.xmind

# SVG（矢量源文件）+ PNG（高清图）+ PDF（单页矢量）
python3 <skill-dir>/scripts/render.py ./mindmap/<主题>.md --outdir ./mindmap
```

`<skill-dir>` 就是本 SKILL.md 所在目录。两个脚本都是零第三方依赖的纯 Python。

常用参数：

- `md2xmind.py --structure logic-right` —— 换成逻辑图/树形图/组织架构图等布局（默认 `unbalanced` 思维导图）
- `md2xmind.py --title "标题"` —— 覆盖中心主题
- `render.py --only svg,png` —— 只要其中某几种
- `render.py --scale 4` —— 指定超采样倍率（默认按画布自动选）
- `render.py --layout wing` —— 强制两翼布局（默认 `auto`：节点多到图变成窄长条时自动切两翼）

**产物清单**

| 文件 | 能改吗 | 用途 |
|---|---|---|
| `.md` | ✅ 纯文本 | 真相来源。改这个，然后重跑上面两条命令 |
| `.xmind` | ✅ Xmind 里直接编辑 | 交付、协作、二次加工 |
| `.svg` | ✅ 矢量，Illustrator / Figma / Inkscape 可编辑 | 精修排版、嵌网页 |
| `.png` | ❌ 图片 | 贴文档、发消息、插 PPT |
| `.pdf` | ❌ 矢量单页 | 打印、正式汇报 |

**失败处理**（不要伪造文件，也不要声称已经生成）：

- 没装 Chrome/Edge/Chromium → `.svg` 仍然会生成，直接告诉用户 PNG/PDF 需要浏览器，或让他用矢量工具自行导出
- 想编辑 `.xmind` 但没有 Xmind → Xmind 免费版可永久编辑本地文件（只有导出 PNG/PDF 才需订阅）；也可用其他支持 `.xmind` 的工具导入

## 图装不下了怎么办

深度放开后，图会变大。**不要靠砍深度来控制规模**，靠拆图：

单张图节点超过约 **180 个**，或某个一级分支自己就超过约 **60 个节点**时，拆成「总览图 + 分支详图」：

- **总览图** —— 全部一级分支，最多到 2～3 层，让人一眼看清全局
- **分支详图** —— 那个庞大的分支单独成图，从自己开始一路展开到叶子

各自是独立的 `.md` 文件，各自转换。别把它们硬塞进一个文件。

## 第 7 步：收尾

给一份简短回执：

- 产物路径清单
- **深度统计**：最大层数 / 主干分支到了第几层
- 节点统计：各层节点数、总数
- 哪些节点标了 `⚠`、为什么（是推断，还是读到一半缺依据）
- 一句话：**改 `.md` 后重跑第 6 步即可，不用重做分析**

## 反模式

- **不要因为「图会变高」就砍深度** —— 该深的地方浅了，图就白画了
- **不要平均用力** —— 主干要深、外围要浅，均匀的浅网没有信息量
- **不要只列名词就收工** —— 「模块 A / 模块 B / 模块 C」是目录，不是分析
- **不要为了凑层数硬拆** —— 拆下去得能说出新事实，否则就是注水
- 不要跳过大纲直接生成 `.xmind` —— 等于放弃了可修改性
- 不要套用固定视图模板 —— 一级分支必须从内容推导出来
- 不要把整句话塞进节点，解释放备注或正文
- 不要读全量代码再画图，成本失控且容易跑偏
- 不要编造结构；宁可少画几个节点，也不要填一个不存在的东西

## 宿主适配

- 不需要 subagent，Codex CLI / Claude Code / 其他 Agent 均可跑
- 只用到「读文件 / 写文件 / 执行命令」三种能力，遵守宿主的权限与审批规则
- 写文件被拦时，说清缺什么权限，**不要假装已经保存**
- 生成 PNG/PDF 要调本机浏览器，若宿主沙箱禁止启动外部进程，走 `.svg` + 提示用户的路径
