# PM Workflow Skill

This skill turns product requirements into working artifacts: PRD HTML, interactive prototype HTML, flowchart HTML, acceptance checklist, demand analysis, and data reports. It is designed for product work across different business domains and product types.

## First Decision

1. If `.agents/workflows/` exists, do not re-initialize. Read the relevant workflow file and continue from the current project state.
2. If `.agents/workflows/` or required scripts are missing, install this skill into the project once (command below).
3. If the user explicitly asks to reinstall or update the workflow, run the same command. Runtime scripts are always refreshed; files the user has edited are kept and the new version is written to `.pm-workflow/updates/` for comparison. Replaced copies are backed up under `.handoff/skill-backups/`.

Install / update — run `scripts/initialize.py` with the platform's Python. It is the single cross-platform installer; `scripts/init.sh` and `scripts/init.bat` are only thin wrappers around it for users who prefer a double-click.

```bash
# macOS / Linux
python3 <skill-dir>/scripts/initialize.py --project .
```

```bat
rem Windows (py is the official launcher; there is no python3 command)
py -3 <skill-dir>\scripts\initialize.py --project .
```

Locating `<skill-dir>`: use your file-search tool (Glob/Grep) for `**/edu-pm-workflow-v2/scripts/initialize.py` across the project and the user's skill directories (`.agents/skills`, `~/.agents/skills`, `~/.claude/skills`, `~/.cursor/skills`). Do **not** shell out to `find` — on Windows `find` is `System32\find.exe`, a text-search tool that takes entirely different arguments, so the discovery step itself would fail before installation ever starts.

## Workflow Routing

Load only the workflow needed for the user's current request:

Artifacts are organized **per requirement**: each requirement gets ONE top-level folder named after it (`[需求名]/`), holding up to seven artifact subfolders — `需求文档/ 原型/ 流程图/ 原型截图/ 需求挖掘/ 验收清单/ 数据分析/` plus `沟通记录.md`. `scripts/`, the two start-service entries (`启动原型导出服务.command` on macOS, `启动原型导出服务.bat` on Windows), `.handoff/`, `关键点.md`, `.agents/` stay at the project root and are shared across requirements.

**Folder ownership (applies to ALL four workflows):** Whichever workflow runs first creates `[需求名]/`. Before writing, every workflow first checks whether `[需求名]/` already exists — if so it reuses that folder and drops its output into the matching subfolder; if not it creates `[需求名]/`. PRD is **not** assumed to come first: a requirement may begin with demand discovery or data analysis, and all later steps reuse the same `[需求名]/`. Only create the subfolders actually used — never pre-create empty ones. Use an identical `[需求名]` across every workflow so all outputs land in one folder.

| User intent | Read this file first | Primary output |
|---|---|---|
| New requirement, PRD, prototype, flowchart, continue PRD work | `.agents/workflows/edu-pm-prd.md` | `[需求名]/需求文档/[需求名]-PRD.html`, `[需求名]/原型/[需求名]-prototype.html`, `[需求名]/流程图/[需求名]-flow.html`, `[需求名]/流程图/[需求名]-screenflow.html` (交互流程图, as needed) |
| Demand discovery, user needs, competitive/product insight | `.agents/workflows/edu-pm-demand.md` | `[需求名]/需求挖掘/[需求名]-需求洞察.html` |
| Acceptance checklist, test checklist, launch verification | `.agents/workflows/edu-pm-acceptance.md` | `[需求名]/验收清单/[需求名]-验收清单.html` |
| Metrics, BI-style analysis, report from data | `.agents/workflows/edu-pm-data-analysis.md` | `[需求名]/数据分析/[需求名]-数据分析.html` |

For PRD work, treat `.agents/workflows/edu-pm-prd.md` as the authoritative project workflow. Do not use root-level `edu-pm-prd.md` if both exist.

## PRD Workflow Rules

- **Confirm the requirement before writing when core information is missing; ask only focused questions.** The six-dimension completeness check has a **材料** dimension (§1.2): ask once for the tracking dictionary, design spec / brand accent, and any existing prototype screenshots — finding out at §数据埋点 that no dictionary exists means interrupting the user mid-draft or inventing field names.
- **Carry the confirmation into the document.** §1.4 maps each confirmed item to its PRD location: 核心改动 → 功能清单+详细方案; 成功指标 → 需求目标表; **不做 / 范围外 → 需求概述的「范围块」**; 背景证据 → 需求背景三段式; 跨页规则 → 需求概述规则表; 待确认项 → 正文末尾清单. A "不做" that was agreed verbally but never written into the PRD does not count as confirmed.
- **Copy `assets/templates/prd-content.html` and fill it in — do not hand-write the HTML skeleton.** That file already carries the right class names, table headers, `colgroup` widths, `.desc-block` structure and `data-preview` placeholders; nearly every historical defect (descriptions using `<br>` instead of `<p>`, wrong column counts, missing `colgroup`) came from rebuilding the structure from memory. **Since v2.7 the skeleton also carries its own `<style>` block — copy it too, never delete it and never replace it with a shorter hand-written version.** It pins three things that used to be prose-only rules and kept getting dropped: tables are `width:100%` + `table-layout:fixed` (so `<colgroup>` sets proportions and no content can blow the column out), `img.proto-shot` is `max-width:100%; height:auto` **and must not carry a hardcoded `width=`/`height=`** (a hardcoded width bypasses the CSS — one real PRD shipped `<img width="1600">` around a 3200px PNG and pushed the table to `scrollWidth 1811` in a 1500px viewport), and `iframe.flow-frame` gets an explicit height (an unsized iframe falls back to the browser default 300×150).
- **Run `assets/scripts/validate_prd.py` before delivery and report the result honestly.** It mechanically checks: core chapters present, 项目信息/版本记录 not merged, no standalone boundary chapter, continuous chapter numbering, all six table headers and column counts, meta-table is two-column, every 详细方案 row has `data-preview` and a non-empty 原型 cell, description cells use `.desc-block` with no `<br>` and no multi-number cramming, snake_case tracking names with six columns, `#prdContent` contains its own `<style>`, and the goal table header. A pass does NOT mean the document is good (visual and editorial quality still need human review) — but a failure means it is definitely not done.
- **Fixed chapter order, tailored to the requirement's size — do not force all sections.** Order is 项目信息 → 版本记录 → 需求背景 → 需求目标 → 需求概述 → 业务流程图 → 交互流程图 → 详细方案 → 数据埋点 → 时序图（上线计划/附录 only if genuinely needed）. Core skeleton always kept: 项目信息, 版本记录 (two separate tables — never merged), 需求背景, 需求目标, 详细方案. The other seven (需求概述/业务流程图/交互流程图/数据埋点/时序图/上线计划/附录) are dropped when the requirement doesn't need them. Never drop sections silently — state which are kept/dropped and why during requirement confirmation. If 业务流程图 is dropped, skip producing the flowchart file; if 交互流程图 is dropped, skip the screenflow file. See edu-pm-prd.md §2.2 and §1.3.1.
- **No standalone 异常/边界 chapter.** Boundary cases live in the owning row's 【边界说明】 block inside 详细方案 (§2.3.1), never as a document-level chapter.
- **需求目标 states the user outcome and how it is measured, not implementation actions.** Quantifiable goals go in a 用户结果/衡量指标/统计口径/预期方向/目标值 table; with no real baseline write 「待基线确认」 — never invent a percentage. Non-quantifiable goals must still be observable and verifiable. Same rule for numbers cited in 需求背景: give the source or mark it unconfirmed. See §2.2 ④.
- **The 原型 column accepts a high-res screenshot (`img.proto-shot` with real width/height, optionally linked to the clickable prototype) or an interactive iframe — do not convert existing screenshots into iframes.** See §2.3 and §3.3.
- **详细方案 description cells: two mandatory blocks, the rest by a written test — not by habit** (§2.3.1). 【页面元素】and【交互说明】are mandatory in every cell. For any optional block the test is: **"if this page were deleted, would the rule still hold?"** If yes, it is a cross-page rule and belongs in the 需求概述 rule table (§2.3.1 ③), not repeated in each cell — 签到 1/3/7-day reward tiers, cumulative score/quota accounting, grant timing, role-permission matrices and global rate limits are the usual offenders. If no, it belongs to this page. Typical symptoms of over-writing: the same shared rule copy-pasted into three cells, or four-plus blocks in one cell. 【功能逻辑】 in particular should carry only rules that stop being true when this page is gone. Also: never write "同上" / "详见 x.x" — a row gets copied into review documents on its own; never pad with "无"; every item is its own `<p>`/`<li>` inside a `.desc-block`; multiple numbered items crammed into one paragraph is a defect. Absolutely no technical API/interface wording in description cells.
- **One row = one screen or one state variant** (§2.2 ⑦). A 二级功能 spanning three screens becomes three rows, each with its own prototype asset; a screen's multiple states stay in one row and are enumerated in 【页面元素】. If you cannot name the single image the 原型 cell shows, the granularity is wrong.
- **需求概述 is more than a feature list** (§2.2 ⑤): it carries a **范围块** (本期范围 / 本期不做什么·暂不展开) plus the feature-list table plus, when needed, the cross-page rule tables (`h3` + small table). If the whole chapter is dropped for a small requirement, the 范围块 and rule tables must relocate — 功能清单 may go, but "what we are NOT doing" and the shared rules may not.
- **需求背景 is three parts** (§2.2 ⑥): who hits what problem in what scenario → what impact it has → what evidence supports it (state plainly when there is none; never invent). **需求目标** closes with a 「待后续确认的产品口径」 list collecting every 待确认 in the document, each with owner and impact.
- **The edit module ships undo/redo** (§2.7 ⑤): ⌘Z / Ctrl+Z undo, ⌘⇧Z / Ctrl+Y (also Ctrl+⇧Z) redo, covering text edits, row add/delete, table delete and column/row resize on one stack; a new edit clears the redo branch. Deleted rows/tables are kept alive as **DOM nodes** in the stack (not HTML strings) so restored controls still work, and the native contenteditable undo must be `preventDefault`ed in the capture phase or both stacks fire at once. History is memory-only — never promise it survives a refresh. Since v2.5 **undo also has a permanent button** — the third slot of the top bar (§2.10); keyboard-only was measured as "no entry point at all". Redo deliberately gets no button (the six navs are fixed).
- **时序图 (sequence diagram)** is an optional dev/QA-facing PRD chapter placed AFTER 数据埋点 (the last body chapter): copyable **Mermaid source-code text blocks — never rendered images or iframes** (devs/QA reuse the text directly; a rendered picture was rejected). Contains an end-side orchestration `sequenceDiagram` (real participants, e.g. 用户/端/Cocos/服务端) plus a key-object `stateDiagram-v2`, each block with a "复制源码" button and 说明 bullets. Technical field/interface names ARE allowed in this chapter (the §2.3.1 ban only covers 详细方案 description cells). See edu-pm-prd.md §4.7.
- **交互流程图 (screen flow)** is an optional PRD chapter placed before 详细方案: one whole image-style HTML canvas stitching all core screens (scaled live prototype iframes) with labeled **right-angle (Manhattan-routed) arrows** for navigation — never bezier curves or diagonal lines; same-side loop-back edges run on offset rails — plus an explicit state-machine legend. Produce per edu-pm-prd.md §4.6; export via the local screenshot service.
- Produce HTML artifacts, not Markdown artifacts, unless the user asks otherwise.
- Keep PRD, prototype code, prototype screenshots, and flowchart synchronized. When one changes, inspect the others for necessary updates — and treat the prototype code as the source of truth that the PRD's images must be re-rendered from (§3.9).
- The HTML prototype is the primary interactive artifact. Pencil is optional visual enhancement only.
- **Scroll-sync must reach three levels — page, state, and element. Page-level alone is NOT done** (edu-pm-prd.md §2.6 ⑧, §3.4.2, §3.4.3). L1 `data-preview="page-id"` switches the iframe's page. **L2 `data-preview-state="state-key"`** is required on any row whose 【交互说明】 describes "click X → becomes Y" (a modal opens, an entry greys out, a result state shows) — the page must NOT change, the state must. **L3 `data-preview-focus="element-key"`** points at the one element the row is about. Three hard implementation rules: (1) **never reset `iframe.src` for a row on the same page** — every `src=` is a full reload that wipes the state you just set, which is the usual reason "state-level sync looks like it does nothing"; only change `src` when the page actually changes, and **re-send the state after the reload completes**; (2) the prototype must expose an enumerable state/element registry plus an **idempotent `apply()`** that reuses the real business functions (never a parallel "demo" implementation) and a machine-readable `<script id="pm-preview-registry">` copy for validation; (3) the prototype must **acknowledge with `pm:applied {seq, ok}`** — a missing/`ok:false` reply must surface as a visible "this page only supports page-level sync" marker in the panel, never a silent no-op. Cross-origin `file://` iframes cannot be scripted from the parent, so postMessage is the only channel — a prototype without a receiver can only ever be page-level. When the host page legitimately cannot be modified, degrade to L1 + screenshots, **delete the unused `data-preview-state`/`-focus` attributes**, and tell the user which rows were degraded and why.
- **PRD and the prototype code are ONE deliverable, not two** (edu-pm-prd.md §3.9). Producing or updating a PRD **must modify the prototype code in the same pass**, and every image in the PRD's 原型 column **must be a real render of that code**. Three hard rules: (1) never ship a PRD whose prototype code was left untouched — handing the user a merge-notes list to apply themselves is not a substitute; (2) images come only from the local export service rendering the real HTML — never hand-drawn, never produced in a design tool, never copied from another project, never a leftover screenshot from a previous round; (3) one image ↔ one addressable screen or state in the code, and **every code change must be followed by a re-render** — each `原型截图/*.png` mtime must be ≥ its prototype code's mtime. Which code counts as "the prototype code" is decided by the §3.0 landing question (in-place edits → the host product pages; workspace → that workspace's prototype HTML; full new version → the product pages in the new version directory). **Order matters: change the code → run it → render via the export service → put the PNG into the PRD.** Drawing the image first and back-filling code guarantees a design mockup rather than an implementation. Before delivering, report verifiable numbers (files changed + mtimes, image↔screen mapping, mtime comparison), not just "done".
- **A prototype IS the product — never publish review-only chrome into it** (edu-pm-prd.md §3.10). Every screen the prototype renders must look exactly like the feature will look once it ships. The only test: **would this element or this sentence still be there in production?** Yes → keep it (if it is the product's own copy). No → delete it (it exists only for this review). Four things are banned: (1) **"this is demo data" disclaimers / badges / watermarks** — a real case injected `<div class="usage-demo">演示数据 · 此原型用于产品评审，非客户真实使用统计</div>` whenever no real data was present; (2) **review labels in the nav / top bar** — a real case shipped `<b>AI会议 · V2 交互评审</b><span>演示数据</span>`; (3) **stylesheets or scripts loaded only for the review** — a new `v2-review-artifacts.css`, or a `.usage-demo{…}` rule added to the host's own polish stylesheet; (4) **a query param that makes a page render an extra declaration** (`?review=1`). **Fake data is made identifiable by the data itself** (names, dates, numbers that read as samples), never by a banner — and if somewhere must say "this data is fake", that somewhere is the PRD, not the prototype. The trap that produced this: the older wording "demo data should be identifiable **in the copy**" was read as "declare it in the UI". **"Identifiable" means the data is identifiable, not that the UI must declare itself.** Do not over-correct in the other direction either — tips that belong to the product must stay (a host page's existing `<div class="endtip">安全提示：群机器人地址等同于该群的发送权限，请勿外发…</div>` is product copy; deleting it breaks the product), and added UI must reuse the host's own variables / class names / components rather than starting a parallel visual system. Mechanical check: `validate_prd.py` → `validate_surface()` resolves the prototype HTML **plus the local scripts/styles it links**, strips comments, and fails on any of 非客户真实使用 / 用于产品评审 / 仅供评审 / 评审专用 / 交互评审 / 此原型 / 本原型 / 演示数据.
- **Ask the prototype mode before writing any prototype — never default it** (edu-pm-prd.md §3.0). Three questions, asked even when the user does not raise them: (1) **form** — static gallery (browse-only), interactive prototype (one clickable window walking the whole flow), or both; (2) **source** — generate from scratch, or build on an existing codebase; (3) **landing** — only when the source is an existing codebase: **edit the host pages in place**, **ship a self-contained requirement workspace + `MERGE-NOTES.md`**, or **produce a full new version directory cloned from the baseline**. "Existing code" is ambiguous and must never be assumed: it can mean a prototype this workflow generated earlier, the user's real product codebase, or another interactive prototype. **Make the user name the exact path** — the deliverables differ completely. Building on a real codebase must NOT reuse this workflow's default class names (`.device` / `.rail` / `.chip` / `.titem` / `.tabs` …) or its default Tailwind + Font Awesome CDN stack. Measured against one real static-page project, only 2 of 30+ class names overlapped (`btn`, `modal`).
- **Always ask the landing question (3) when working on a real codebase — never infer it from precedent.** The three landings produce completely different artifacts: in-place edits on the baseline, a review-ready workspace that still needs a manual merge, or a runnable full version. Naming an option "new v1.5.0 directory" without spelling out the artifact shape has already caused one user to read it as a full version while the model built a bare workspace — both sides believed they were right, and the product codebase ended up untouched. A prior version folder in the repo is evidence that a workspace pattern exists, **not** permission to pick it: put it in the option description and let the user choose. After delivering, self-verify against the landing's own check (host page mtime changed + new entry greppable / no product pages and a `MERGE-NOTES.md` present / product page count matches the baseline) and **report those verifiable numbers, not just "done"**.
- **§3.1 规范 and §3.2 设计规范 describe the from-scratch default ONLY — they do not apply when building on an existing codebase** (edu-pm-prd.md §3.0 问二). Those sections hard-write the Tailwind + Font Awesome stack, the `.device` / `.gallery` container classes, and the output path `[需求名]/原型/[需求名]-prototype.html`. When 问二 = B, rules 2/4/6/9/10/11 of §3.1 and the class/size conventions of §3.2 are all void — follow §3.7.2 instead. Only §3.1 rule 12 (prototype ↔ PRD content alignment) applies either way. Quick test: **is the file I am about to write located at `[需求名]/原型/[需求名]-prototype.html`?** Yes → §3.1 applies; no → go to §3.7.2. This gate matters because §3.1 is read *before* §3.7, and it is exactly how a from-scratch default once overrode an existing-codebase run.
- **Building on an existing codebase: recon first, then implement** (edu-pm-prd.md §3.7). Before writing a line, identify: tech stack (can dependencies even be added?), the **host page that actually owns these screens**, the naming/prefix style, where styles live, which shared `*.css`/`*.js` are in play, the existing modal/toast components, the repo's own conventions (`docs/*PRD.md`, `verify-*.mjs`, `MERGE-NOTES.md`), and any similar prior feature. **Report the recon conclusion — including which landing you are producing — and get confirmation before implementing.** If the host page cannot be found, stop and ask — never guess; a user-named host page once turned out to contain none of the tabs or buttons the prototype showed. Then implement in that repo's own idiom, and place the output according to the confirmed landing: **in-place** edits to the host pages (never under `[需求名]/原型/`), a **workspace** holding only this round's artifacts plus a `MERGE-NOTES.md` merge list (no product code copied), or a **full new version directory** cloned from the baseline and runnable as-is. Either way, update whatever companion artifacts the repo requires.
- **An interactive prototype is NOT a thin wrapper file — when host code exists, iterate on the host code** (edu-pm-prd.md §3.8, corrected in v2.5). The older rule ("produce `[需求名]-prototype-flow.html` alongside the gallery") produced a shell containing one review banner plus an `<iframe>` around the real page — which both violates §3.10 (review label in the nav bar) and invents a layer the product never decided on. Instead: **if the user gave host code, modify that code in place** (§3.0 问三 landing); **add a page only when one is actually needed**, naming it in the host's own style (e.g. the `transcript-*` / `translate-*` prefix family — see §3.7.2); if no page is needed, edit what exists. Only when there is no host code (§3.0 问二 = A) do you start from §3.1's `[需求名]/原型/[需求名]-prototype.html`. Interaction comes in three tiers — page navigation, component state, business rules — and **the third tier (business rules) must be separately confirmed; never fake it by hard-coding a plausible-looking result**. Keep state in one JS data object, reusing the host's store rather than starting a parallel one. **Quick test: will this file still exist after the feature ships? No → it is a shell; delete it and put the interaction in the real pages.**
- **The PRD's action surface is a fixed six-button top bar — and editing requires a login** (edu-pm-prd.md §2.10). Exactly six `data-pm-nav` buttons, in this order: `dual-pane` 双栏预览 / `edit` 编辑 / `undo` 撤销 / `save` 保存 / `prototype` 交互原型 / `gallery` 静态图册 — no more, no fewer, no reordering, and **"导出" does not get a slot** (that capability is the bottom-left 「一键复制全文」, §2.8, which stays put). The bar lives in `<body>`, **outside `#prdContent`**, and it replaces the old bottom-right `.fab-group` / `.save-btn-container` — leaving those in place yields two save buttons whose states disagree. Three states drive everything: **guest** (not logged in, **service unreachable**, `PM_READ_ONLY`, or a `viewer` role — all four collapse to the same row) shows 「编辑」 but greys out undo/save and leaves **zero `contenteditable` in `#prdContent`**; **signed in**; **editing**. Never ship "the page is editable and only fails at save time" — the user has already rewritten a document by then. Guest mode must still be a fully readable document. Accounts live in `<project>/.pm-workflow/users.json` (already gitignored by the installer; `pbkdf2-sha256`, 120k rounds, per-user salt) and are created with `py -3 scripts/start_service.py --add-user 张三` (`python3` on macOS) — put that exact command in the error message rather than saying "no permission". Session tokens are stateless HMAC strings sent in the `X-PM-Session` header, **not cookies** (the PRD is often opened over `file://`, where cookies to `127.0.0.1` hit third-party-cookie policy); `updated_by` is resolved **server-side from the session**, never from a client-supplied name. The change log has four columns — **修改人 / 修改时间 / 修改内容 / 位置** — and the server persists it in two places: the JSON log next to the PRD and an injected `<script type="application/json" id="pm-change-log">` block **before `</body>` and outside `#prdContent`**, so it travels with the file to the intranet while never contaminating 「一键复制全文」. **Never write the change log into the document body as an appendix** — pasted-out PRDs then end with an internal audit trail that reviewers mistake for requirement content. The static gallery page reuses this exact bar and title block (differing only in `data-pm-topbar="gallery"` and the absence of the user chip / log panel), and hides it via `body.pm-embedded` when framed. **The interactive prototype page carries none of this** — no `.topbar`, no `data-pm-nav`. Two implementation traps cost real debugging time: unlock must restore **the original `contenteditable` value** (writing back `"true"` promotes §2.7's `.editable-table-wrap` to editing host, so the `td` never receives focus and the whole undo/change-tracking chain goes silently dead), and `saveAll()` must `blur()` the active element first (§2.7 debounces input by 600ms, so the change list reads as empty otherwise). Mechanical check: `validate_prd.py` → `validate_topbar()`.
- **v2.6 reverses v2.5's "intranet visitor = guest" rule, and adds a one-click "re-render figures" tool** (edu-pm-prd.md §2.9 / §2.11). **Editability depends only on whether *this browser* can reach the service and has an account — not on whether it is the author's own machine.** `start_service.py --lan` binds the LAN address, so a colleague opening `http://<your-LAN-IP>:<port>/` can log in and edit the file on your disk, with the change log attributing it to them. The DNS-rebinding defence is *not* relaxed: the test changed from "origin must be loopback" to **"the Host header must point into the machine's own address set"** — `evil.com` resolving to 127.0.0.1 still fails, because the Host header reads `evil.com`. Take the LAN address from a **UDP probe** (`connect(("10.255.255.255", 1))`, sends nothing, lets the kernel pick the default egress interface) — `gethostbyname(gethostname())` returns the wrong address on machines with VPN or virtual adapters. Writable LAN hosting **requires at least one editor account**; with none it must refuse to start and print the `--add-user` command (otherwise a colleague opens it and nobody can edit — much harder to diagnose than an error). Always print the cost with the URL: **that machine must stay awake, and a changed LAN IP breaks the old link.** The 「重新出图」 button sits in a `.topbar-tools` group to the right of the six fixed navs, **separated by a divider and carrying no `data-pm-nav`** — it is a *tool* (one action on this document), not a *nav* (somewhere to jump to); `validate_topbar()` now fails a PRD whose tools group is missing or whose `#navRefigure` carries `data-pm-nav`. Server side: `/api/figure-status` diffs every `<img>` in the PRD against the manifest — the **content signature** is the primary test (render params `scale`/`viewport` are recorded at export time so the signature can be recomputed; any byte change in rendered code flips it), with **mtime only as a fallback for pre-v2.6 manifests** (note: `touch` alone must NOT flip the verdict — the signature hashes content, so "unchanged content ⇒ still fresh" is correct behaviour, not a bug). Only **fixable** figures get the amber dashed outline and the "· N stale" badge; manually-placed images under `原型截图/` are `unmanaged` and never touched, and figures whose source prototype was deleted are `manual` (reported, never outlined — outlining something the server cannot repair is misleading). One click re-renders **all stale sources** server-side via Playwright (**no AI needed or wanted**: the verdict is a fingerprint and the output is a render, both deterministic), then cache-busts **only the figures it actually re-rendered** with a `?v=` query — without that the browser serves the old PNG from cache and the user sees "badge cleared but image unchanged". Finally, v2.5 shipped a **session-key bug that forced a re-login on every reload**: the localStorage key includes `projectId`, which comes from *dynamically loaded* `pm-runtime-config.js`, so the module-init read used `pm-session:default` while `login()` wrote `pm-session:<projectId>`. Read the session lazily, once the config has arrived.
- **v2.7 fixes three defects that only show up when you actually click the PRD — a passing `validate_prd.py` did not catch any of them** (edu-pm-prd.md §2.2 / §2.9 踩坑 2 / §2.11 ⑧). (1) **The static-file route is a deny-list, not a directory allow-list.** `_serve_file()` used to require the URL to *contain* an artifact directory name (原型 / 流程图 / 需求文档 …); the intent was "only serve artifact folders", but it also blocked **host product pages**, which live at the project root — so a §3.0 landing-A run 404'd on `/ResourcePanel.html` and its `.css`/`.js`, blanking the dual-pane preview, breaking the interactive-prototype page and dropping images from 一键复制全文. Now: anything under the project root with an allowed extension, excluding dot-directories and dependency dirs. The security boundary did not move — `_is_under()` still blocks traversal, and `.pm-workflow/users.json` is `.json`, outside the extension list. **Do not "tighten" it back into an allow-list.** (2) **「重新出图」 must be wired, not just present.** A real PRD shipped `<button id="navRefigure">` with no `hidden` and none of the §2.10 ⑤ JS: every mechanical check was green while the button did nothing on click. `validate_topbar()` now requires all three — `hidden` on the button, `PMService.figureStatus()` (status + stale outline), `PMService.refigure()` (the click actually calls `/api/refigure`) — and the same `hidden` on the gallery page's copy. (3) **Skeleton CSS**, per the previous bullet.
- Use the local PNG export service through `scripts/prototype-export-client.js`; do not build new `html2canvas`/`html-to-image` exporters.
- **「一键复制全文」must turn prototype iframes into inline base64 images** via `POST /api/snapshot` on that same local service (cache-first, auto re-render on stale) — never `iframe.remove()`, which silently drops every prototype from the pasted document. Under `file://` the browser blocks both local `fetch` and canvas readback, so base64 can only come from the service; do not add a front-end screenshot library for this. Degrade in three explicit tiers and always tell the user what was lost. See edu-pm-prd.md §2.8.
- **When pasted images look blurry, raise `MAX_IMG_WIDTH` — do not touch the encoder.** Measured on real assets: JPEG .85, JPEG .95, lossless PNG and WebP .92 are indistinguishable once all four are downsampled to 1200px; the detail is lost in the resize, not the compression. Ship 2000px at quality 0.9. Verify by zooming a pasted image past 1000px — at the default in-document width (≈335px, fixed to the table's 原型 column) every resolution looks identical, so "looks fine pasted" proves nothing. Report clipboard size as the base64 payload (1.33× the decoded bytes), not the decoded bytes. See edu-pm-prd.md §2.8 ⑤.
- **`原型截图/` is the PM's asset folder, not the tool's scratch folder.** When an export run clears "last round's output", delete only the filenames this HTML registered in `.export-manifest.json` — never glob `*.png`. That glob has already wiped 8 hand-made screenshots (captured state-by-state from `[需求名]-shots.html` and hand-named, referenced directly by the PRD's 原型 column) during an export of a `-prototype.html` that produced a single image. Those PNGs are not in git. See edu-pm-prd.md §4.4 item 6.
- **The dual-pane preview is CLOSED by default** (§2.6). The PRD opens as plain readable prose; the panel appears only when the user clicks 双栏预览 — which since v2.5 is **the first button of the top bar** (`[data-pm-nav="dual-pane"]`, §2.10), not the old bottom-right floating toggle — the label flips to 收起预览, and the iframe `src` stays empty until first open so nothing loads in the background. A non-empty prototype folder is NOT a reason to auto-open. The only automatic open is an explicit `#preview=<page-id>` deep link.
- **The dual-pane preview must ship zoom controls** (`－ / % / ＋ / 适配`, same control group as §4.6), keeping `previewZoom` in a JS variable only — never written into the DOM, so saved/copied output stays clean. See edu-pm-prd.md §2.6 ⑨.
- **Business flowcharts must NOT use Mermaid's default theme** (§4.1). `theme:'default'` produces saturated blocks with white text that clash with the light PRD shell. Use `theme:'base'` with the fixed `themeVariables` block (near-white node fill `#faf9ff`, thin `#cbc4e7` border, dark `#30285b` text, `lineColor #8d82b1`), `flowchart.curve:'linear'` for right-angle connectors, `nodeSpacing:60`/`rankSpacing:70` as minimums, and the shared page shell (`#f8f8fc` body, white 14px-radius card). Distinguish node types by shape, not fill colour.
- **Zero text overlap is a hard gate for both diagrams, not a best effort** (§4.3 ②, §4.6 ③④). Fix order when the audit fails: enlarge the canvas → widen gaps → reroute/add rails → split into two canvases. Never fix overlap by shrinking type, hiding a label, deleting the offending branch, or using a background colour as a cover-up. Deliver only after the geometry audit returns `ok:true` AND you have looked at the diagram at 100% zoom both standalone and inside the PRD iframe — a diagram that is clean at 60% can still be overlapping when embedded. See §4.6 ④ for the audit snippet and the export-time guard that blocks shipping an overlapping diagram.
- **Anything the PRD does over `http://` must survive an insecure context.** On the intranet `navigator.clipboard`, `ClipboardItem` and `showSaveFilePicker` do not exist: the copy path needs an `execCommand` fallback. The export service must resolve the calling page by project-relative path too, or `/api/snapshot` and `/api/asset` return 400 and 一键复制全文 silently loses every image. **v2.6 changed who is a guest**: it is no longer "anyone not on the author's machine" but **"anyone who cannot reach a running service"**. With `--lan` the service is reachable from the intranet, so a logged-in colleague can genuinely edit the author's file (v2.5's blanket "intranet visitor = guest" over-corrected and made collaboration impossible); a **static copy with no service behind it** is what stays read-only. The v2.4 illusion to keep avoiding is the *file-picker fallback* — saving a local download while the published copy never changes. See edu-pm-prd.md §2.9.
- Before delivery, verify scripts render and the prototype pages match the PRD descriptions, and run `validate_prd.py`.
