v2.5（服务运行时 3.4.0 · 2026-10-14）
【问题】：PRD 这一侧的"能看"和"能改"长期是两件事，而"改"这条路走得不干净。用户这次把三件事一次说清：「**1. 生成的仅 PRD 的 html 支持编辑、保存、导出，且编辑的 PRD 在右上角保留修改记录、修改人、修改内容、修改时间。2. PRD 的 html 需要登录才可编辑，游客仅可查看；3. PRD 的右上角有几个快捷导航，包括"双栏预览"，"编辑"，"撤销"，"保存"，"交互原型"，"静态图册"几个固定的导航，其中"静态图册"页的导航以及标题栏与 PRD 页的保持统一。交互原型页不要增加导航，保持原功能代码的展示。**」

拆开看是三处结构性缺口 + 两处实测坑：

| # | 缺口 | 实测证据 |
|---|---|---|
| 1 | **编辑权限根本没有门** | v2.4 之前，只要 `prototype_server.py` 起得来、`_authorized()` 通过，**任何人保存都算数**——本机/内网访客和文档作者在服务端**完全同权**。§2.9 那张能力表里"可编辑 / 只读"是**客户端自觉**，服务端不认人，保存出来的记录也无人可署名 |
| 2 | **保存与导航散在两处** | 保存是左下角 `.fab-group` 的「💾 保存」、双栏预览是 §2.6 的另一颗浮标、撤销**只有快捷键**；顶栏位置空着。要对照着用，得在三处之间找 |
| 3 | **改动记录不存在** | 保存一次只产生一个 `.bak` 备份，**改了哪几处、谁改的、什么时候改的，全无痕迹**；评审现场"这版和上版差在哪"只能靠人肉 diff |
| 4 | **交互原型页被迫写"薄外壳"** | §3.0 问一 C 与 §3.8 旧文要求生成 `[需求名]-prototype-flow.html`——用户拿到的是一层本流程的跳转壳，里面 iframe 套他**已有的**原型。用户的更正原话就是：「**不要单独写薄外壳的 -prototype-flow.html，用户会提供已有的代码，在已有的代码基础上修改，如果需要新增页面时再新增，不需新增时就在已有代码的基础上修改。修改页面的命名也要参照以前代码命名的风格。**」 |
| 5 | **解锁的写法把变更追踪打哑** | 实测：解锁时一律把 `contenteditable` 写回 `"true"`，会连 §2.7 的 `.editable-table-wrap`（原本 `contenteditable="false"`）一起升级成编辑宿主。浏览器把焦点交给它，`td` 收不到 `focus`/`input`——**`activeElement` 变成 `DIV.editable-table-wrap`，探针数组为空、`data-changed` 不亮、`canUndo()` 为 false，整条追踪与撤销栈静默失效** |
| 6 | **保存读得比写入早** | 实测：`saveAll()` 立刻读 `data-changed`，而 §2.7 的 input 有 **600ms 去抖**——不先结算，改动清单读成空，记录写成"保存整篇"、`where` 为空 |

第 4 条与第 1 条其实是同一个毛病的两端：**工具（外壳、保存按钮、服务端口）被当成了产品的一部分**，于是"薄外壳"要写、服务一连上就等于有编辑权。

【思路】：
1. **顶栏六导航，顺序写死不许变**（§2.10 ①）：`dual-pane` 双栏预览 / `edit` 编辑 / `undo` 撤销 / `save` 保存 / `prototype` 交互原型 / `gallery` 静态图册。**"导出"不占导航位**——那是 §2.8 左下角的「📋 一键复制全文」，别混进来。顶栏必须挂在 `#prdContent` **之外**（否则会被一键复制带走）。
2. **权限三态，判定口径只有一条**（§2.10 ②）：游客 / 已登录·阅读态 / 编辑中。**能写文件才叫"可编辑"**——服务连不上、没配账号、`PM_READ_ONLY`、`viewer` 角色**四种情况全落进"游客"**，统一置灰 + 不挂 `contenteditable`。这条口径把 v2.4 之前那种"内网访客直接连服务就能保存、以为改上去了"的**假编辑**一次性消掉。
3. **登录门禁做在服务端，不做在页面上**（§2.10 ③）：`.pm-workflow/users.json` 存账号，口令 `pbkdf2-sha256` + 12 万轮 + 每用户独立 salt（`pbkdf2$<salt>$<hex>`），接口 `GET /api/me`、`POST /api/login`、`POST /api/logout`、`GET|POST /api/change-log`；`/api/save-html` **先 `authenticate()` 再走 revision 比对**，返回 `updated_by` / `change`。建号命令要能直接抄：`python3 scripts/start_service.py --add-user 张三 --name 张三 --password xxx --role editor`（另有 `--list-users` / `--remove-user`）。**报表要能抄**：没配账号回 428 且附建号命令，口令错 401，viewer 403。
4. **会话走无状态签名，不走 cookie**（§2.10 ③）：`base64url(username.expiry).hmac-sha256`，密钥＝项目 token；请求头 `X-PM-Session`，前端存 `localStorage`。**不用 cookie 是因为 PRD 常以 `file://` 打开**，cookie 在这种场景下不可靠。`authenticate()` 每次都回查 users.json，**账号被删/会话过期立刻失效**，不做服务端会话表。
5. **改动记录四列 + 两处存储**（§2.10 ④）：`修改人 / 修改内容 / 修改时间 /（版本）`。① 全量流水写 `[需求名]/需求文档/.pm-change-log.json`；② 同时注入 HTML 的 `<script type="application/json" id="pm-change-log">`，**位置必须在 `</body>` 前、`#prdContent` 之外**——随文件走又不被 §2.8 的复制带走（实测位置：`main 结束 167 < 记录块 287 < </body> 739`）。渲染与写入时序写死三步：**收改动 → 先结算再读 → 以服务端为准回刷**。
6. **两个实测坑写进规范，而不是只留在记录里**（§2.10 ⑤）：
   - 解锁 `contenteditable` 必须**按原值存档再恢复**——把原值存进 `data-pm-locked`，解锁时 `orig === '' ? 'true' : orig`；**一律写回 `"true"` 就会把 `.editable-table-wrap` 变成编辑宿主、静默废掉追踪与撤销**（对应上表第 5 条）。
   - `saveAll()` **必须先 `blur()` 再读** `data-changed`，并 `await` 一个 tick 让 600ms 去抖落地（对应上表第 6 条）。
7. **静态图册页与 PRD 页统一外壳**（§2.10 ⑥）：两页的顶栏与标题栏**逐项一致**（差异只允许两处），图册页顶栏根节点标 `data-pm-topbar="gallery"`；被 iframe 嵌入时用 `body.pm-embedded` 自动隐藏顶栏——**判定用 `window.self !== window.top` 自检，不用 URL 参数**（避免又长成 §3.10 那类"参数驱动的界面声明"）。
8. **交互原型页零导航**（§2.10 ⑦）：**不写薄外壳**，直接在用户已有的代码上改；需要新增页面时才新增，命名**参照原代码风格**。§3.8 旧文里那段要求生成 `-prototype-flow.html` 的写法**已作废**，改写成四种来源情况的对照表 + 一句话判据「**这个文件，产品上线后还会不会存在？**」——不会 → 是外壳 → 不写。
9. **把可机械判定的部分做进 `assets/scripts/validate_prd.py`（新增 `validate_topbar()`）**，六项检查：六个导航齐不齐 + 顺序对不对 / 顶栏在不在 `#prdContent` 之外 / 有没有残留 `.fab-group`、`.save-btn-container` / 图册页导航与标题栏是否逐项一致 / 交互原型页有没有被我方加顶栏 / 有没有残留 `*-prototype-flow.html` 薄外壳。**正反例各 7 组实跑**（正例 0 error；缺撤销 → 2 error；残留 `.fab-group` → 1；顶栏进正文 → 1；图册页导航不一致 / 标题栏不一致各 → 1；原型页被加顶栏 → 1；存在薄外壳 → 1）。**在真实项目上试跑即命中**：`AI会议产品/会议总结一键外发-PRD.html` FAIL，精确点名"缺顶栏导航 + 残留 `.fab-group`"——影响面符合预期。
10. **§2.6 / §2.7 / §2.4 收口到顶栏**：§2.4 保存整段重写（保存动作归顶栏）；§2.6 的浮标段标注"v2.5 兼并进顶栏"、双栏预览改用 `navDualPane`；§2.7 的 `EXCLUDE_SELECTOR` 加 `.topbar, .changelog-panel`，⑤ 撤销从"只有快捷键"改为"**快捷键 + 顶栏常驻按钮**"（重做仍不占按钮位）；§2.8 `stripSkeleton()` 删除清单加 `.topbar, .changelog-panel, #pm-change-log`。**关键点：顶栏与记录面板不许进 `#prdContent`**，否则一键复制会把工具 UI 抄进交付附件。
11. **实测验证**：**浏览器 E2E 33 项断言全绿**（顶栏结构 / 游客态 / 登录框 / 登录后编辑态 / 改动+保存 / 撤销 / 交互原型置灰 / 落盘产物 / 退回只读 / 无 JS 报错）；**图册页与持久化 16 项全绿**（六导航与标题栏逐项一致 / 独立打开顶栏可见 / iframe 嵌入时 `body.pm-embedded` 生效 / 新标签打开图册页 / 登录后从内嵌块读出历史记录）；**服务端接口 E2E 9 组全过**（登录三条失败路径 / 未登录保存 401 / 正确保存 `updated_by == "张三"` / 记录注入且块唯一 / 登出）；**服务端鉴权单测 8 组**（散列不可逆 / 篡改签名失效 / 过期失效 / 删号后会话立刻失效 / users.json 损坏容错）。
12. SKILL.md 同步：`version: 2.5.0`；description 补顶栏六导航 + 登录门禁 + 改动记录 + 图册页统一 + prototype 无导航；**§3.8 那条规则整条改写**（不再是 "second file"）；**新增一整条 §2.10 规则**（六按钮、三态、账号、会话、四列记录、两处存储、图册页，含两个实现陷阱）；undo 那条补"v2.5 起有常驻按钮"；双栏预览那条补"是顶栏第一个按钮"；§2.9 那条补"内网访客就是游客"。README 同步升 v2.5 沿革，并加一条 ⚠️「**旧 PRD 会校验变红**」。

v2.4（服务运行时仍为 3.3.0 · 2026-10-14）
【问题】：原型里长出了「评审专用」的内容。用户验收时的原话是：「**在 skill 明确告诉 AI 在创建原型时不要在原型中备注"演示数据，此原型用于产品评审，非客户真实使用数据"，以及多余不必要的提示（比如在导航栏上还有提示）。风格要与现有的代码保持统一，不要有过多的提示。**」

在 `v1.4.1`「多账号 v2」那次产出里逐条对得上：

| # | 长出来的东西 | 实测证据 |
|---|---|---|
| 1 | **免责横幅** | `resource-panel.js:52`——`isDemo` 为真时注入 `<div class="usage-demo">演示数据 · 此原型用于产品评审，非客户真实使用统计</div>` |
| 2 | **导航栏评审标签** | 交互原型顶部 `<b>AI会议 · V2 交互评审</b><span>演示数据</span>`——正是用户说的"在导航栏上还有提示" |
| 3 | **评审专用样式 / 脚本** | 新增 `v2-review-artifacts.css`；给宿主页挂上 `resource-panel.polish.css` 里的 `.usage-demo{…}`（还配了 `content:"i"` 的圆形图标）。宿主库原本只有 `official-pages.css` / `resource-panel.css` 那一套 |
| 4 | **参数驱动的界面声明** | `?review=1&demo=1` 让宿主页多渲染出一整块提示条 |

根因是**一句规范被读反了**：**§3.8 第 4 条旧文「假数据可辨认：演示数据在文案上可识别」**——"在文案上可识别"被理解成"必须在界面上声明它是假数据"。横幅、导航标签、评审专用 CSS 全是从这一条长出来的。

【思路】：
1. **把判据压成一句问话**：这个元素 / 这句话，**产品真上线后还会不会出现？** 会 → 留（哪怕它只是提示，**只要是产品自己的文案**）；不会 → 删。把这句写进 §3.10 开头当唯一判据。
2. **新增 §3.10「原型即产品：不许出现『评审专用』内容」**，明确禁止四类——免责横幅/角标/水印、导航栏评审标签、只为评审加载的样式/脚本、`?review=1` 之类参数驱动的界面声明；每类都配上表里的实测证据。
3. **改写根因句 §3.8 第 4 条**：从"演示数据在文案上可识别"改为"**辨认的是「数据」，不是「界面」**"——假数据统一收在数据对象顶部，靠**数据本身**（人名 / 时间 / 数值看得出是样例）被认出来；**禁止**在界面上加任何"这是演示数据"的声明。并在该条下挂历史注记，写清旧措辞是怎么被读反的。
4. **给出"假数据正确做法"对照表**（做对 ✅ / 做错 ❌）：需要说清"数据是假的、来源在哪" → **写进 PRD 的【数据与内容规则】列**，或交付时用文字说明，**不要写进原型界面**（否则评审时分不清哪句是产品要做的文案、哪句是原型作者的注解）。
5. **写清"不要过度纠正"的边界**：宿主页**原本就有**的产品提示必须保留——实测例子是 `<div class="endtip">安全提示：群机器人地址等同于该群的发送权限，请勿外发；已保存的地址在页面上以掩码显示。</div>`，**这是产品文案、不是评审装饰，删掉就是改错产品**。原型外壳（画廊页 / 交互原型页的顶栏与切换按钮）是**工具**、允许存在，但外壳上不许写评审话术，且外壳要尽量薄。
6. **风格统一条款**：新增 UI 一律复用宿主页已有的变量 / 类名 / 组件（挂靠 §3.7.2 第 1–4 条）；宿主库没有的样式体系，不许为了评审另起一套。
7. **四处加门禁**：§3.1 加第 13 条（从零生成也适用）、§3.2 加"提示要克制 · 风格跟宿主统一"、§3.7.2 加第 8 条（不许往宿主库塞评审专用物）、§3.6 逐页校验表加第 9 项、§3.7.3 自检清单加一条。
8. **把可机械判定的部分做进 `assets/scripts/validate_prd.py`（新增 `validate_surface()`）**：
   - 抽出公共解析 `_prototype_files()`（从 `validate_scroll_sync` 里提炼），再向外扩一层 `_surface_files()` = **原型 HTML + 它在本地引用的 `<script src>` / `<link href>`**。这一层是必须的：反例里的横幅在 `resource-panel.js` 里，**只扫 HTML 必然漏掉**。
   - 新增 `_strip_comments()`：去掉 HTML / JS / CSS 注释后再扫，**替换成等量换行以保住行号**。这一层同样必须：`/* 首次进入时的演示数据。真实环境由服务端下发。 */` 这类注释是合法用法，不剥就会误报。
   - `REVIEW_MARKERS` 只收无歧义的字样：`非客户真实使用` / `用于产品评审` / `仅供评审` / `评审专用` / `交互评审` / `此原型` / `本原型` / `演示数据`。
   - 命中就报「**文件:行号 + 命中词**」，直接定位到那行代码。
9. **实跑验证三组**：① 真实 PRD（落点 A → v1.4.2 宿主页，扫到 12 个文件，含 `AIPC-Detail.html` 里那两条"演示数据"注释）→ **PASS**，证明注释不误报；② 合成 PRD 指向 v1.4.1 → **FAIL 并精确点名** `resource-panel.js:52 命中「非客户真实使用」`；③ 纯注释样本 → 不报。全部符合预期。
10. SKILL.md 同步：`version: 2.4.0`；description 补 review-only chrome；**新增一条独立规则**写全四类禁止 + 判据 + 根因陷阱 + "不要过度纠正"的边界 + 脚本能力。
11. §5.2 加 1 条 ★（原型无评审专用内容），并**更新脚本能力说明**（补上 v2.3 的滚动联动与本节的原型洁净度，同时写明"脚本只扫得到写死的字样，抓不出『产品上线后根本不会有』的那类元素"）；§5.3 第 14 项补一句"不许顺手塞进评审专用内容"。
12. **已验证 / 未验证**：**脚本部分已实跑验证**（三组用例全过，真实反例被精确点名到行）；**"这一屏明天上线会不会显得奇怪"这一条只能人工逐屏看**——脚本永远判断不了。


v2.3（服务运行时仍为 3.3.0 · 2026-10-13）
【问题】：双栏预览的滚动联动**只做到页面级**。用户在真实产出上验收时的原话是：「**产品需求文档的双栏滑动时，滑动到页面中有弹窗时，右侧的原型没有打开对应的弹窗。没有做到完全的同步，只是做到了页面级的同步。没有做到元素级和按钮级。**」

拿那份真实 PRD（`会议总结一键外发/需求文档/…-PRD.html`）实测，三处断点都是结构性的：

| # | 断点 | 实测证据 |
|---|---|---|
| 1 | **寻址只到页面这一层** | `data-preview` 全篇只有 2 个取值（`d-detail` / `a-channel`），而详细方案有 **9 行**——`d-detail` 吃掉 6 行、`a-channel` 吃掉 3 行。滚过同一页的多行时，右侧什么都不变 |
| 2 | **没有状态通道** | 原型侧 `summary-send.js`（416 行）导出了 `runSend` / `commitSend` / `SEND_RULES` 等业务函数，但**没有任何对外接收接口**——无 `postMessage` 监听、无 hash/query 解析。父页就算想指定状态也无处送达 |
| 3 | **换页方式摧毁状态** | PRD 侧 `switchPage(v)` 无条件 `iframe.src = url` —— **每次赋值都是一次整页重载**，会把刚设好的状态与滚动位置全部冲掉 |

第 2 条的根因是浏览器模型：原型常以 `file://` 加载（跨源 iframe），**父页读不到 `contentDocument`、调不了里面函数、点不了里面按钮**，`postMessage` 是唯一通道。所以"元素级同步做不到"不是代码写漏了，是**根本没修这条路**。

【思路】：
1. **把滚动联动从"页面级"重定义为「三级同步」，逐级写死判据（§2.6 ⑧）**：
   | 级别 | PRD 侧 | 右侧表现 |
   |---|---|---|
   | **L1 页面级** | `data-preview="page-id"` | 换 iframe 目标页 |
   | **L2 状态级（按钮级）** | `data-preview-state="state-key"` | 页面**不换**，页面内进入该状态（弹窗打开 / 入口置灰 / 成功态） |
   | **L3 元素级** | `data-preview-focus="element-key"` | 页面**不换**，把该元素滚进可视区并高亮 |
   并给出**逐行判据**：该行【交互说明】里有"点 X 之后变成 Y" → 至少到 L2；【页面元素】点名的那个元素是评审看点 → 补 L3。
2. **§3.4.2 新增三级同步的主指令 `pm:goto`**（`{type,page,state,focus,seq}`）与**回执 `pm:applied {seq, ok}`**；写清 `navigate` 是旧协议、**只能到 L1**，保留兼容但新 PRD 一律发 `pm:goto`。**回执必须写死为刚性要求**——没有它，父页分不清"设好了"和"原型压根不支持"，这正是"以为做了元素级同步、实际只到页面级"的来源。
3. **新增 §3.4.3「原型侧：状态与元素注册表」**，要求原型提供三样东西：① **可枚举注册表**（`PM_PREVIEW.states` / `.focus` + 机器可读的 `<script id="pm-preview-registry">`）② **幂等的 `apply()`**（先复位默认态再应用目标态；不播放入场动画）③ **消息接收端**（收 `pm:goto` → 调 `apply` → 回 `pm:applied`）。附完整参考实现（约 30 行）。
4. **三条硬约束**：① 状态必须**复用真实业务函数**（`openSendPanel` / `setSendEntryDisabled` …），**不许为 PRD 预览另写一套"看起来对"的演示逻辑**（那会同时违反 §3.9 与 §3.6）；② **key 不许编**——引用了注册表里没有的 key，原型必须回 `ok:false`；③ **注册表要与 §3.8 可交互原型的"状态集中管理"共用同一份状态定义**，不许写成两套。
5. **写死"同页只发状态、绝不重设 `iframe.src`"**，并给出原因（每次 `src=` 都是整页重载）；**换页后必须补发一次 `pm:goto`**，否则换页那一行的状态会丢。§2.6 ⑧ 的示例 JS 整段重写，含 `lastKey` 去重、`seq` 配对、800ms 超时判降级、`previewStateTip` 可见提示。
6. **降级规则表格化**：宿主页/原型**可以改**（落点 A 改的正是本次要动的文件；落点 B 本来就要写）→ 按 §3.4.3 实现，对本次新写的 JS 只是约 30 行、**不是额外污染**；宿主页**不该为预览而改** → 降级到 L1 + 静态图并写明哪几行降级、**且把那几行的 `data-preview-state`/`-focus` 删掉**，不许留着假装存在；预览指向**截图版 HTML** → 每个 hash 场景当做一个 `state` 接进注册表即可支持 L2。
7. **把可机械判定的部分做进 `assets/scripts/validate_prd.py`（新增 `validate_scroll_sync()`）**：
   - **① 同页多行不可区分**：同一 `data-preview` 取值下若有多行在 `(state, focus)` 上完全相同 → FAIL（这既是"只到页面级"的症状，也违反 §2.2 ⑦「一行 = 一个界面或状态变体」）。
   - **② 与原型注册表对账**：尽力从 PRD 里解析出原型 HTML（含 `PRD_REPO` 前缀拼接、`CATALOG.url`、绝对 `file:///` 路径），读其 `#pm-preview-registry`，逐个核对 PRD 引用的 `state`/`focus` 是否真的存在；**解析不到注册表但 PRD 用了这两个属性 → FAIL**（说明 key 无法被证明存在，可能静默失效）。**解析不出原型文件时一律跳过，不制造假阳性。**
8. **实跑验证**：真实 PRD 上立刻量化出问题——`d-detail 6 行 + a-channel 3 行 = 9 行`全部没有 state/focus（正是用户说的"只到页面级"）。另建三组合成用例：key 存在 → PASS；key 不存在 → FAIL 并点名该 key；用了属性但找不到注册表 → FAIL。全部符合预期。
9. §5.2 加 4 条 ★（三级做到位 / key 与注册表对账 / 同页不重载 / 回执失败可见）；§5.3 第 15 项并入 state/focus 与注册表同步；§2.6 ⑩ 深链接支持 `#preview=<page-id>@<state-key>` 并在换页后补发。
10. SKILL.md 同步：`version: 2.3.0`；description 补 three-level scroll-sync；**新增一条独立规则**写全三级 + 三条实现铁律 + 跨源限制 + 降级要求。
11. **已验证 / 未验证**：**脚本与规范文本已实跑验证**（真实 PRD 量化 + 三组合成用例全过）；**"右侧真的把弹窗打开了"这一条只能在浏览器里人工确认**——脚本能证明 key 对得上、行不可区分，证明不了动画与视觉。下次验收时按 §5.2 那 4 条 ★ 逐条实测。


v2.2（服务运行时仍为 3.3.0 · 2026-10-12）
【问题】：v1 到 v2.1，全篇关于 PRD 与原型的关系只有一句软话——§5.3 的「必须遍历整份 PRD 以及关联的原型、流程图同步更新」，SKILL.md 也只是「Keep PRD, prototype, and flowchart synchronized」。**没有任何一条要求：① 产出 PRD 时必须真实修改原型代码；② PRD 里那几张界面图必须是原型代码渲染出来的。** 结果就是"PRD 可以独立于代码存在"——文档完整、图也齐全，但代码没动。实测后果（v1.5.0 那次）：产出目录 36 个文件、PRD / 原型 / 流程图 / 截图一应俱全，**但宿主产品页 `AIPC-Detail.html` 的 mtime 仍停在 2026-08-26（一个多月前）**，全库 grep 本次新功能的类名 `send-entry` / `发送总结` / `推送渠道` **0 命中**；36 个文件里 20 个是 PNG 截图。用户的结论是「**并没有修改源码，也没有生成新的代码**」。

同一处还有第二个口子：**§2.3 / §3.3 允许原型列放"高清截图"，并把"已有稳定截图"列为优先项**——"已有"二字对来源没有任何约束，等于给"用上一版的旧图""从别处拷一张相似的图""用设计工具另画一张示意图"全都开了门。图一旦不是本次代码渲染出来的产物，评审时照图提问、研发照代码实现，**两边从一开始就不是同一个东西**。

【思路】：
1. **新增 §3.9「PRD ↔ 原型代码 强绑定（产出 PRD 必做 · 图必须由代码渲染）」**，开篇写死一句话：**PRD 里的每一张界面图，都必须是"本次真的改过的那份原型代码"在浏览器里跑出来的真实页面。代码是源，图与 PRD 文字是它渲染出来的产物。**
2. **三条铁律 + 反例**（每条都配"不合格的样子"，便于对照判）：
   | # | 铁律 | 不合格的样子 |
   |---|---|---|
   | 1 | 产出/更新 PRD 时，**必须同步真实修改原型代码** | 只出 PRD 与说明文档、代码一字节没动；或只出「改动清单 / `MERGE-NOTES.md`」把改动留给用户自己做 |
   | 2 | PRD「原型」列的每张图，**必须是原型代码的真实渲染** | 手工画的线框图；设计工具另做的示意图；从别处拷来的相似页面图；上一版遗留的旧图 |
   | 3 | **一图 ↔ 代码里一个可寻址的界面或状态** | 一张图拼两个界面；或代码里没有这个页面，图是"设想中的样子" |
3. **「原型代码」指哪一份，锚定 §3.0 问三的落点**——不另设概念：A 就地改宿主页 → 宿主产品页；B 独立工作区 → 工作区里的 `原型/[需求名]-prototype.html`；C 新版本全量目录 → 新版本目录里的产品页。**并特别写明落点 B 同样要求代码被真实改过**（那个 HTML 是本次真写出来的，不是空壳、不是只有截图；打不开/点不动/PRD 里的界面在里面找不到，铁律 1 就没做到）。
4. **固化产出顺序**：`改原型代码 → 浏览器里跑起来 → 用本地导出服务渲染出 PNG → 把 PNG 放进 PRD`。**明确禁止"先画图再补代码"**——那样出来的必然是设计稿而不是实现。图只能走 `scripts/prototype-export-client.js` → `prototype_server.py` → Playwright/Chromium，**不许 `html2canvas` / `html-to-image`，也不许画图工具手工出图**。
5. **加时间戳校验**：`原型截图/*.png` 的 mtime 必须 **≥** 对应原型代码的 mtime。图比代码旧 = 图陈旧 = 不合格。这条是"代码改了但忘了重出图"的唯一有效防线。
6. **把时间戳校验做进 `assets/scripts/validate_prd.py`（新增 `validate_provenance()`）**——不落到脚本上的"必须"等于没说。它机械地查两件必真的事：① PRD 里 `img.proto-shot` 引用的图文件**必须真实存在**（在此之前，图片 404 是能 PASS 的）；② 该图 mtime **不得早于**本次原型代码的 mtime。**判不了的（落点 A/C 的代码在宿主库、整份 PRD 全用 iframe、找不到可比的原型 HTML）一律跳过不报错**，避免假阳性。实测四个分支：图比码旧 → FAIL；图文件缺失 → FAIL；纯 iframe → PASS（跳过）；图比码新 → PASS。**第一次跑就抓到了真问题**：项目里那份真实 PRD 的 8 张截图全部比 `会议总结一键外发-prototype.html` 旧 74 秒——即最后一次改代码之后没有重出图，按新规则判不合格。
7. **自证要求写成必须报数字**（不许只说"已完成"）：① 本次真实改动的原型代码文件（路径 + mtime，或 `git diff --stat`）；② 「PRD 里 N 张原型图 ↔ 原型代码里 N 个界面」，逐个列 `图文件名 → 代码里的 hash / 类名`；③ 「N 张图 mtime 全部 ≥ 代码 mtime ✓」。
8. **§3.6 一致性自查升级**：加"图 ↔ 代码溯源"为第 8 项检查；流程里插入"按 §3.9 用导出服务渲染出图（代码改了必须重渲染）"环节；交付声明模板从"共 N 个页面已核对，全部通过"改为**必须带 §3.9 的三项数字**。并写明 §3.6 与 §3.9 的分工：**§3.9 管溯源（图是不是从代码渲染的），§3.6 管内容（代码里的文案/数据/状态与 PRD 对不对得上），两道都要过。**
9. **堵 §2.3 / §3.3 的口子**：§2.3 原型列加硬约束（图必须是原型代码真实渲染 + 代码改了必须重渲染 + 不存在"只出 PRD、代码没动"的交付）；§3.3 把「**已有稳定截图优先**」改成「原型依赖后端跑不起来、或需要贴进钉钉/飞书时优先」，并补一句**「已有」不等于可以用——不是本次代码渲染出来的图就是陈旧或别处的图**。
10. **§5.2 加两条 ★ 检查项**（§3.9 铁律 1 / 铁律 2+3），其中铁律 1 明确写"只出了 PRD / 只出了改动清单、代码没动 → 直接判不合格"；并把校验脚本的能力说明更新为"含原型图溯源；**脚本只能保证图不是陈旧产物，保证不了代码被改过**"。
11. **§5.3 迭代规则**：第 14 项由「原型文件（.html）」改为「**原型代码（真正被改的那份）**」并写死"PRD 一改，原型代码必须同批真实改掉"；新增第 14.1 项「**原型截图**」专管重渲染与 mtime 校验；第 18 项交付前加 §3.9 自证；铁律与 Why 补上"PRD 与原型代码是同一批改动，三者同批交付"以及"第二类更严重的失真发生在 PRD 与代码之间"。
12. SKILL.md 同步：`version: 2.2.0`；description 补一句 PRD↔prototype-code binding；**新增一条独立规则**写全三条铁律 + 落点映射 + 固定顺序 + 必须报数字；原「Keep PRD, prototype, and flowchart synchronized」一句扩为"原型代码是源头，PRD 的图必须从它重渲染"。
13. **已验证 / 未验证**：脚本部分已实跑验证（四分支 + 真实 PRD 抓出 74 秒陈旧图）；**规范文本部分尚未在真实项目上再跑一遍完整流程**。下次用到 §3.9 时重点回收两项：① 交付回复里有没有 §3.9 的三项数字；② 图与代码的时间戳核对是不是真做了（而不是嘴上说做了）。

v3.1（服务运行时 3.3.0）
【问题】：v3.0 把常驻启动器设成「默认不装」（见下一条第 6 点），于是**自动启动这条链路等于没有**——浏览器点「一键导出」/「一键复制全文」时去叫 launcher_port，那儿没人应答，每次都弹「导出服务没有启动，请双击…」。用户要的是：点导出就自动把服务起起来，不用先双击任何东西。而默认装一个常驻进程到别人机器上，仍然是不合适的。

【思路】：
1. **socket 激活解开这个两难**：plist 里只给 `Sockets`，不给 `RunAtLoad`、不给 `KeepAlive`——**端口由 launchd 自己持有**。空闲时本项目在 `ps` 里一个进程都没有，端口却照样应答；浏览器一连上来 launchd 才把 `prototype_launcher.py` 拉起，它起完服务、空闲 120 秒自退。既是自动启动又不留常驻，所以才敢改成 **macOS 上随安装默认注册**（`install_launcher.sh` 退居重注册/卸载入口；注册失败只警告不中断安装）。取套接字用 libSystem 的 `launch_activate_socket()`（ctypes）；非 launchd 环境下它返回 ESRCH(3)，属预期情况而非错误，据此回退到自己 bind。继承 fd 必须 `HTTPServer(..., bind_and_activate=False)` + 关掉占位 socket + `os.dup(fd)`：自己 bind 会直接撞 EADDRINUSE——那个端口正被 launchd 占着。
2. **在 launchd job 内部调 `launchctl bootout` 等于自杀**（实测踩过一次，是本轮最坏的一个坑）：bootout 杀的就是这个 job 的进程，而那正是**正在处理这次请求的自己**——请求得不到回应，注册还停在半路（bootout 成功、bootstrap 没跑成），`launchctl list` 从此查无此 job，自动启动彻底失效、只能手动重装。防线是 `pm_launchagent.IN_LAUNCHD_JOB`：socket 激活分支里**赶在起服务之前**置上，`sync()` 见到就直接返回。
3. **启动器端口固定，不随端口自愈漂移**：`derive_ports` 的 salt 只作用于服务端口。plist 里端口是写死的，改它只能 bootout + bootstrap，即上面那条自杀路径；让它永不漂移，这个竞态就从根上不存在。真会跟别的应用撞车的本来也只有服务端口。
4. **端口预留不许去探启动器端口**：`reserve_ports` 只探 `config["port"]`。探 launcher_port 必然"bind 不上"——它要么被 launchd 长期持有（socket 激活的实现方式就是如此）、要么被独立运行的启动器自己持有，两种都是**正常状态**；而它又不随 salt 变，一旦判成冲突就是 8 次空转后报「连续多次都没抽到可用端口」。这两个后果都实际撞到了：先是每次启动端口都漂、plist 随即陈旧，后是独立启动器模式下直接起不来。
5. **端口同步只放在 `reroll_ports` 里**——那是全局唯一改动端口的地方。放到调用点上，每新增一条自愈路径都得记得补一次同步，迟早漏；漏一次 launchd 就守着一个没人访问的旧端口，自动启动静默失效。
6. **`--doctor` 要能区分「被 launchd 持有」和真冲突**，否则正常状态会被报成故障。启动器端口若真被外人占了，**不能说"启动时会自动换端口"**（它不会），要给出"停掉占用方后重跑 `install_launcher.sh`、期间双击入口照常可用"的实际指引。
7. Windows 本版仍不做自动启动（已确认的取舍）：服务本体就是用户开着的那个窗口，没有东西需要被拉起。客户端文案按 `navigator.userAgent` 选词，Windows 上照旧提示双击 `.bat` 并保持窗口。
8. 联动更新：README（自动启动条目、「不留常驻进程」条目、§二启动方式、§四改写为按需启动器）、SKILL.md 目录结构、edu-pm-prd.md §3.1-7 与目录树、本文件。
9. **已验证 / 未验证**：macOS 实跑——零进程冷启动 → 点导出 → 5 秒内 2/2 张 PNG 落盘；服务端口被外部进程占用时只有服务端口重抽、plist 与注册纹丝不动；`/api/snapshot` 返回 base64 且二次命中缓存；卸载后 doctor 如实报「未注册」；未注册 LaunchAgent 时独立启动器模式照常工作且不自退；空闲 120 秒自退后端口仍应答、再点导出照常拉起。**Windows 依然没有实跑**，仍只有静态检查。


v3.0（服务运行时 3.2.0）
【问题】：skill 分享给同事后，导出/截图在别人机器上起不来。逐条核实的根因有六个，其中前三个叠加起来完整解释了"双击启动脚本没反应"：① **升级等于没升级**——安装器判定"文件已存在且 hash 不在 installed.json 里 → 视为用户自定义，不覆盖"，而老项目首次升级时 installed.json 是空的，于是**每个既有文件都被判成自定义而保留**，服务代码永远停在旧版；② 因此残留的旧 `.command` 探测固定端口 8765，服务却在别的端口；③ 一个几天前没退出的旧服务仍占着 8765，使②的探测恒真，`.command` 直接 `exit 0` 什么也没做。另外三个是结构性的：④ 缺 `runtime.json` 时在**模块导入期**裸抛 FileNotFoundError，而该目录是 gitignore 的，任何人 clone 项目仓都会撞上且无自救路径；⑤ LaunchAgent 的 label 全局唯一，**一台机器只能服务一个项目**，后装的覆盖先装的；⑥ Windows 完全没有可用路径（没有 `.bat` 入口、安装器是 bash、`python3` 命令不存在、用了 `os.execve`）

【思路】：
1. **安装器按文件分三类，这是①的正解**：运行时代码（`pm_runtime` / `pm_bootstrap` / `start_service` / `prototype_server` / `prototype_launcher` / 导出客户端 / 两个启动入口）**永远覆盖 + 时间戳备份**，不做冲突检测——用户本来就不该手改这些；用户会编辑的（4 份 workflow 说明书、PRD 骨架、绘图提示词）保留冲突检测，新版写进 `.pm-workflow/updates/`；`关键点.md` 和 `.mcp.json.example` 只在缺失时创建。再补 `scripts/known_hashes.json` 收录历代已发布版本的 hash，让"文件等于某个旧发布版"被认成没改过而直接升级，不误判成自定义。另外补上安装器一处都没有的 `chmod +x`（`copy2` 只保留源文件模式，zip/网盘中转会丢权限位 → 双击无反应）和 `.gitattributes`（`*.command` 锁 LF、`*.bat` 锁 CRLF，否则 Windows 检出再传回 Mac 会得到 `bash: $'\r': command not found`）
2. **端口改为按项目确定性推导到 20000–32767，且可自愈**：不再固定 8765/8766，一台机器上多项目各用各的端口；原先用 `bind(port=0)` 抽的是 OS 临时端口段（49152+），恰是系统派给出站连接的范围。启动时端口不可用就换一对重新推导并回写配置。异常处理从子串匹配 `"Address already in use"` 放宽到 `OSError`——Windows 上被 Hyper-V/WSL/Docker 保留的端口抛的是 `WSAEACCES(10013)`，表现为 PermissionError，错误文本里根本没有那句英文。占用者若是本项目自己的服务则正常退出，不能换端口（否则会起出第二个服务）
3. **`ensure_config` 取代 `load_config`，修 ④**：配置缺失时就地创建而不是抛错，导入期不再有可失败的 IO
4. **Windows 路径**：新增 `启动原型导出服务.bat` 和 `init.bat`，正文**必须纯 ASCII**（cmd.exe 按控制台 OEM 代码页解码批处理文本，文件名可以是中文，NTFS 是 Unicode）；解释器按 `py -3` → `python` → `python3` 探测，用**打印哨兵**校验而不看退出码（微软商店的 execution alias stub 会打开商店且不可靠地返回 0）；`os.execve` 换成显式两段式 spawn（Windows 上 execve 是 CreateProcess + 父进程立即退出，会让 `.bat` 窗口一闪即关，且 launcher 的 `poll()` 判活永久失效，真服务崩了也看不出来）；子进程 env 固定 `PYTHONUTF8=1` + `PYTHONIOENCODING=utf-8`（服务打印中文横幅，stdout 重定向进日志后会改用 locale 编码，英文区 Windows 是 cp1252 → 启动期 UnicodeEncodeError）+ `PYTHONUNBUFFERED=1`（否则日志块缓冲，进程被杀时整段丢失——"详见 service.log"最需要它的时候恰好是空的）
5. **运行环境移出项目目录并跨项目共享**：venv 改放 `~/Library/Application Support/pm-workflow/` / `%LOCALAPPDATA%\pm-workflow\`，躲开 OneDrive/iCloud 同步风暴、`os.replace` 的 PermissionError 和 Windows `MAX_PATH` 260 超限。截图引擎优先复用系统已装浏览器（Windows `channel="msedge"` 零下载、macOS `channel="chrome"`），没有才回落自带 Chromium，把最容易被公司代理掐断的 150MB 下载变成可选项。实测复用系统 Chrome、零下载
6. **常驻改显式开启，修 ⑤**：安装时不再自动装 LaunchAgent——在别人机器上偷偷留常驻进程不合适。`setup_prototype_export_watcher.sh` 更名 `install_launcher.sh`（装的是 launcher 不是 watcher），label 改为按项目 `com.pm-workflow.launcher.<project_id>`，支持 `--uninstall`，`KeepAlive` 用 `{SuccessfulExit: False}`（`true` 会无视退出码每 30 秒重启一次，项目删了也照拉）。plist 直接指向项目里的脚本而不复制副本，否则升级后副本不同步、变成一份悄悄跑着的旧代码。Windows 本版不做常驻：服务本体就是用户开着的那个窗口，没有东西需要被守护
